# 3.3  הפכו את אישורי הגישה לשירות עצמי

## מה ולמה
סוכנים לא יכולים למלא טפסי "צרו קשר עם מכירות" או להמתין שלושה ימים לנציג יחסי-מפתחים. המבחן מקצה-לקצה של מודול 3 הוא האם סוכן אוטונומי - שניתן לו רק הדומיין שלכם - יכול להשיג אישורי גישה, להשלים את לחיצת היד של OAuth, ולקרוא ל-API שלכם בלי שום אדם בלולאה. אם בלולאה יש שער-אנושי כלשהו, סטאק הפרוטוקולים שמעליה הוא קישוט.

שני חצאים: **(א)** sandbox בשירות עצמי ואישורי שכבה-חינמית בהרשמה, מונפקים תכנותית; **(ב)** בדיקה חוזרת מקצה-לקצה שמריצה את הזרימה המלאה מול לקוחות סוכנים אמיתיים (ChatGPT-User,‏ ClaudeBot) - חברו אותה ל-CI כך ששחרור לא יוכל לשבור בשקט את הגילוי עבור 3.1 ו-3.2. (ריצת הסיכום החיה עם מודל אמיתי היא [5.4](./m5-4-end-to-end-flows.md); ההנחיה הזו מנוקדת על חצי אישורי-הגישה בשירות-עצמי שביקורת יכולה לאמת מעל HTTP.) אישורי שכבה-חינמית הם גם יעד ניצול-לרעה ידוע - מגבלות sandbox וקווי-בסיס התנהגותיים בהנפקה מונעים ממפתחות הדגמה שנשאבו מלהפוך לצינור מחשוב חינמי לגורמים זדוניים.

## ניקוד
- **מאמץ 3/5** - ברובו עבודת מוצר ו-DevEx: מדיניות שכבה-חינמית, נתוני sandbox, אוטומציית הרשמה, ומערך CI שמריץ לקוחות סוכנים אמיתיים.
- **השפעה 5/5** - מכריעה אם סוכנים יכולים להצטרף אליכם. בלעדיה, 3.1 ו-3.2 הן תיאוריה.
- **שינוי חזותי: בינוני** - מוסיף (או משדרג) זרימת הרשמה / פורטל מפתחים עם מפתחות sandbox. הדפים הציבוריים הקיימים לא משתנים.

## שלבים
1. **שכבה חינמית או sandbox בהרשמה, ללא שער-אנושי.** אימייל + אימות זה בסדר; "צרו קשר עם מכירות" לא. ההרשמה הניתנת-להרצה-בידי-סוכן חייבת להסתיים במפתח API עובד.
2. **נתוני הדגמה ממולאים מראש.** חשבונות sandbox מגיעים עם מוצרים, עסקאות, משתמשים והיסטוריה ריאליסטיים כך שהקריאה הראשונה של הסוכן מחזירה נתונים שימושיים במקום רשימה ריקה.
3. **הנפקת אישורים תכנותית - או אפס סוד משותף בכלל.** מעבר להרשמה, חשפו נקודת קצה מאומתת שמנפיקה אישורי לקוח נוספים, מפתחות sandbox מתוחמים, וטוקנים קצרי-חיים -‏ RFC 7591 Dynamic Client Registration הוא הצורה הסטנדרטית, וה-CLI וה-SDK שלכם שניהם קוראים לה. טוב מכך, תמכו במודל מפתח-ציבורי: תנו לסוכן לייצר זוג-מפתחות משלו ולרשום JWKS (או לפרסם ספריית מפתחות), ואז לאמת כל בקשה על ידי חתימה עליה - אותו מנגנון RFC 9421 HTTP Message Signatures כמו ב-Web Bot Auth‏ ([3.2](./m3-2-web-bot-auth.md)). הסוכן מחזיק את המפתח הפרטי ואתם שומרים רק את החצי הציבורי.
4. **פרסמו `/auth.md` - מתכון רישום-הסוכן.** [פרוטוקול `auth.md` הפתוח של WorkOS](https://workos.com/auth-md?utm_source=forter&utm_medium=referral&utm_campaign=agentic-readiness-guide) מתקנן כיצד סוכן מגיע מהדומיין שלכם לאישור-גישה עובד. הגישו קובץ `text/markdown` ב-`/auth.md`, הנפתח בכותרת עליונה `# ...auth.md...` (בדיקת ה-`authMd` של isitagentready.com נשענת על המחרוזת המילולית), עם מקטעים ל-**Discover, Register, Claim, Use, Errors, Revocation**. פרסמו בלוק `agent_auth` קריא למכונה - גם בקובץ וגם במטא-נתוני RFC 8414 / 9728 שלכם מ-[3.1](./m3-1-oauth-discovery.md) - כך שסוכן יפתור *כיצד לרשום את עצמו* בלי לפענח פרוזה. תמכו בלפחות אחת משלוש הזרימות שלו: טענת זהות ID-JAG (ספק הזהות של הסוכן ערב למשתמש, ללא אדם בלולאה), טענת אימייל-מאומת (OTP לאימייל של המשתמש), או רישום אנונימי עם תביעת OTP מאוחרת. הוא מרכיב את OAuth Protected Resource Metadata שאתם כבר מפרסמים: הקובץ הוא הפרוזה, בלוק ה-`agent_auth` הוא נקודת החיבור.
5. **ניטור הצטרפות.** לוח בקרה שעוקב אחר המרת הרשמה-לקריאת-API-מוצלחת-ראשונה, נשירה לפי שלב, זמן-לטוקן-ראשון, ואותות ניצול-לרעה על מפתחות sandbox שהונפקו. האחרון הוא העדשה ל"האם מישהו שואב את השכבה החינמית שלי ומוכר אותה מחדש?" - התשובה היא בדרך כלל כן, וזה נורמלי; השאלה היא אם אתם רואים את זה.
